## 2. M4 锁的细节

### 2.1 文件格式

```json
{
  "pid": 12345,
  "started_at": 1793982600000,
  "heartbeat_at": 1793982605000,
  "plugin_version": "0.1.0"
}
```

- `bridge.lock` 加入 `BRIDGE_FILES` 白名单，仍走 `ensureRealBridgeDir`/`safeFilePath`（拒绝 symlink/junction）。
- 不删除/改写 `.isaac_agent_owner`；锁文件是插件自己的文件。
- 心跳 `5s`，`TTL 30s`；`unref()` 不阻止进程退出。

### 2.2 状态机

| 情况 | 行为 |
| --- | --- |
| 无锁 | `open('wx')` 独占创建 → 持锁 |
| 锁存在，pid 是本进程 | 接管并继续心跳（模块重载/热更新） |
| 锁存在，pid 存活且心跳 <30s | `{ok:false, reason:"lock_held"}`；`isaac_decide` 降级不写 |
| pid 已死或心跳 ≥30s | 视为僵死锁，删除后重新独占创建（抢占） |
| 刚创建但内容尚未写完（空/半截，mtime <2s） | 视为“写入中”，不抢占 |
| 进程退出 | `process.once('exit')` 同步校验 pid 后 `unlink`；崩溃由 TTL 兜底 |

### 2.3 拿不到锁的工具结果

```json
{
  "ok": false,
  "written": false,
  "discarded": true,
  "discard_reason": "lock_held",
  "error_code": "IO",
  "reason_code": "bridge_unavailable"
}
```

`plugin_status` 会转 `degraded` 并累计 `IO`；不调用模型、不写 decision。

### 2.4 双进程测试

用真实子进程（`node lock-worker.mjs`）通过 stdin `go` 同步起跑：

- 两个 worker 同时尝试 `ensureBridgeLock(raceDir)`；
- 断言恰好 1 个 `written:true`，另 1 个 `written:false` 且 `reason_code:"bridge_unavailable"`；
- 断言 `decision.json` 存在且 request 正确；
- winner 写完后保持锁 400ms，确保 loser 不会在 winner 释放后才起跑。

## 3. M1 的扩展约定

- **已知前缀**（`llm` / `rule` / `viewer` / `preset`）严格匹配 `source`；矛盾 → `INTERNAL/invalid`（`assertDecisionLegal`）。
- **未知前缀**：只要 `provider_id` 符合 `^[a-z][a-z0-9_.:-]{2,63}$`，接受；`assertDecisionLegal` 在 decision 顶层写 `x_provider_unknown:"<prefix>"`，供日志/UI/统计区分。
- 不在 `source` 上猜测未知前缀的可靠性；`source` 仍由生产者显式声明（`llm`/`rule`）。
- 这样新增 `seed_lookup:*`、`local_model:*` 不需要改两端校验表；已知前缀仍不被“未知”放行。

## 5. 已知边界

1. **`bridge.lock` 的 pid 存活检测**使用 `process.kill(pid,0)`；容器/权限受限环境可能误判，保留 TTL 兜底。
2. **锁心跳写失败**（磁盘满/只读）不会立即释放；TTL 后其他进程可抢占。
3. **`bridge.lock` 只在 `isaac_decide`/`apply` 获取**；`isaac_state` 只读不拿锁。
4. **多桥目录**：单进程同时操作多个目录会释放旧锁再拿新锁；生产只有一个桥目录。
5. **状态文件本身不做锁校验**（诊断用途，原子写即可）。
